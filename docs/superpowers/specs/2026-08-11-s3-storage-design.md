# S3 Storage Layer

Date: 2026-08-11
Status: Approved, ready for implementation planning

## Summary

Replace the app's direct Supabase Storage calls with a provider-agnostic storage
abstraction backed by the AWS SDK against Supabase's S3-compatible endpoint, and
add tooling for bulk bucket operations.

Two deliverables:

1. `libs/storage/` — a narrow storage interface with an S3 adapter, used by every
   upload and delete call site in the app.
2. Bulk operations — an rclone runbook for backup/sync/migrate, plus a tested
   `orphans` script for finding bucket objects no database row references.

## Motivation

Four goals, all of which the design must satisfy:

- **Large video uploads.** Uploads are currently single-shot `POST`s with no
  multipart support, so large videos are fragile.
- **Remove the XHR hack.** `libs/uploadWithProgress.ts` hand-rolls
  `XMLHttpRequest` purely because supabase-js exposes no progress callback.
- **Portability.** Keep the storage layer S3-generic so the project could point
  at R2, MinIO, or AWS later without rewriting call sites.
- **Consistency.** One S3 mental model shared by the app and the tooling.

## Current state

- All uploads are client-side. The app has no API routes at all.
- `libs/uploadWithProgress.ts` uploads via `XMLHttpRequest` to the Storage REST
  endpoint, authenticated with the user's session JWT, to obtain byte-level
  progress. It also exports `deleteFiles`, which uses supabase-js.
- `app/hooks/useChangeUserImage.tsx` calls `supabase.storage` directly for both
  upload and delete, bypassing `uploadWithProgress` entirely.
- `app/hooks/useCreatePost.tsx` uploads files sequentially and deletes already
  uploaded files if a later step fails.
- `app/hooks/useDeletePostById.tsx` calls `deleteFiles`.
- `app/hooks/useCreateBucketUrl.tsx` builds public object URLs by string
  concatenation. 14 files import it.
- The `media` bucket is public and flat: object keys are bare ids generated by
  `createStorageFileId`, with no prefixes.
- Storage RLS (from `supabase/migrations/0001_init.sql`): public `SELECT`,
  authenticated `INSERT`, authenticated `DELETE`.

## Background: Supabase S3 authentication

Supabase Storage exposes an S3-compatible endpoint with two authentication
modes, and this design uses both:

**Session token** — RLS-enforced and documented as safe for browser use:

- `accessKeyId`: the project ref
- `secretAccessKey`: the anon key
- `sessionToken`: the user's JWT

**S3 access keys** — generated in the dashboard. These bypass RLS entirely and
are server-only. Used exclusively by the `orphans` script.

Endpoint: `https://<project-ref>.storage.supabase.co/storage/v1/s3`. The
`.storage.` host is the direct storage hostname, which Supabase recommends over
the standard project host for large uploads.

**Prerequisite:** the "S3 connection" toggle must be enabled in the project's
Storage settings before any of this functions.

## Design

### 1. Storage abstraction

New directory `libs/storage/`:

| File | Responsibility |
| --- | --- |
| `types.ts` | The `StorageAdapter` interface |
| `credentials.ts` | Async session-token credential provider |
| `s3Adapter.ts` | S3 implementation of the interface |
| `index.ts` | Configured singleton and public exports |

The interface:

```ts
export interface StorageAdapter {
  upload(key: string, file: File, opts?: {
    onProgress?: (percent: number) => void
    signal?: AbortSignal
  }): Promise<void>
  remove(keys: string[]): Promise<void>
  publicUrl(key: string): string
}
```

`libs/uploadWithProgress.ts` is deleted; its two exports are subsumed by
`upload` and `remove`.

Reads do not use the SDK. The bucket is public, so `publicUrl` remains string
construction against a configurable base URL. Only the write and delete paths
go through S3.

### 2. Credentials

`credentials.ts` exports an async credential *provider* rather than a static
credentials object:

```ts
async () => ({
  accessKeyId: projectRef,
  secretAccessKey: SUPABASE_ANON_KEY,
  sessionToken: session.access_token,
  expiration: new Date(exp * 1000),
})
```

The `expiration` field is load-bearing. The AWS SDK re-invokes the provider when
credentials approach expiry, so a multipart upload that outlives the JWT's
one-hour lifetime refreshes instead of failing. A static credentials object
would produce `SignatureDoesNotMatch` after an hour — a failure that only
manifests on the largest uploads.

`projectRef` is derived from the first host label of `NEXT_PUBLIC_SUPABASE_URL`.

Reading the session via `getSession` is correct here: the code forwards the raw
token to a service that validates it server-side, and makes no client-side auth
decision based on its claims.

New environment variables:

- `NEXT_PUBLIC_SUPABASE_REGION` — required, from the dashboard's S3 config page.
- `NEXT_PUBLIC_MEDIA_BASE_URL` — optional. Overrides the base used by
  `publicUrl`. Defaults to `<SUPABASE_URL>/storage/v1/object/public/<bucket>`.
  This is the seam that makes a future CDN or provider swap a config change.

For the `orphans` script (server-side, never `NEXT_PUBLIC_`):

- `SUPABASE_S3_ACCESS_KEY_ID`
- `SUPABASE_S3_SECRET_ACCESS_KEY`
- `SUPABASE_SERVICE_ROLE_KEY`

`.env.example` is updated with all of the above.

### 3. Upload path

`s3Adapter.upload` uses `Upload` from `@aws-sdk/lib-storage` with an 8 MB part
size and `queueSize: 4`. `lib-storage` sends files below the part size as a
single `PutObject` and only escalates to multipart above it, so avatar uploads
do not pay for machinery they do not need.

Progress comes from the `httpUploadProgress` event, converted to a percentage
and passed to `onProgress`. The percentage contract is unchanged, so
`useCreatePost`'s multi-file progress aggregation needs no modification.

The SDK is loaded through a dynamic `import()` inside the adapter so it stays
out of the initial bundle for routes that never upload.

Call-site changes:

| File | Change |
| --- | --- |
| `app/hooks/useCreatePost.tsx` | Swap `uploadFileWithProgress`/`deleteFiles` for `storage.upload`/`storage.remove` |
| `app/hooks/useChangeUserImage.tsx` | Replace direct `supabase.storage` calls |
| `app/hooks/useDeletePostById.tsx` | Swap `deleteFiles` for `storage.remove` |
| `app/hooks/useCreateBucketUrl.tsx` | Body delegates to `storage.publicUrl`; signature unchanged |

`useCreateBucketUrl`'s signature is deliberately preserved so its 14 importers
are untouched.

### 4. Error handling

Existing behavior is preserved:

- `useCreatePost` still deletes already-uploaded files when a later step fails.
- A missing session still throws `"You must be logged in to upload files"`.
- S3 errors are mapped to readable messages, matching what the current XHR
  implementation extracts from JSON error bodies.

One addition: on a failed multipart upload the adapter explicitly aborts the
multipart upload. Incomplete multipart uploads do not appear in object listings
but still consume billed storage. `lib-storage` handles this for ordinary
rejections but not for an abrupt page close, so the abort is explicit.

`signal` is part of the interface but no cancel UI is built. Out of scope.

### 5. Bulk operations

**`docs/media-operations.md`** — an rclone runbook. rclone already handles
backup, sync, and migrate against the S3 endpoint with concurrency, resume, and
checksum comparison. Writing a custom copy engine would duplicate it for no
gain. The runbook contains the remote configuration block and concrete commands
for each operation, each shown with its dry-run flag first.

**`scripts/media/orphans.ts`** — run via `tsx`. This is the one operation with
no off-the-shelf equivalent, because it must join bucket contents against
application tables.

Algorithm:

1. Paginate `ListObjectsV2` over the bucket, collecting keys and
   `LastModified`.
2. Read `posts.video_url` and `profiles.image` using the service role key.
3. Expand every `video_url` through `getPostStorageFileIds` from
   `app/utils/postMedia.ts`. Image posts store an encoded value
   (`images:id1,id2|audio:id3`), so reusing the app's own parser is what
   prevents live files being classified as orphans.
4. Add `profiles.image` values and the configured placeholder avatar to the
   referenced set.
5. Diff.

Safety properties, since this command deletes data:

- **Report-only by default.** `--delete` must be passed explicitly.
- **`--min-age`, default 24h.** Objects newer than this are never deleted. A
  file uploaded between step 1 and step 2 is otherwise indistinguishable from an
  orphan.
- **Zero-row guard.** If the database query returns no rows, the script exits
  with an error. That state is what a misconfigured connection looks like, and
  without the guard it means "delete everything."

### 6. Testing

Add Vitest and an `npm run test` script. No network access in tests.

Both Vitest and `tsx` must resolve the existing `@/*` path alias from
`tsconfig.json`, since the script and its tests import `getPostStorageFileIds`
from `app/utils/postMedia.ts`.

The core is extracted as a pure function:

```ts
planOrphans(
  bucketObjects: { key: string; lastModified: Date }[],
  referencedKeys: Set<string>,
  opts: { minAge: number; now: Date },
): { orphans: string[]; skipped: string[] }
```

Test coverage:

- `planOrphans`: correct diffing; min-age exclusion; the placeholder avatar
  never being flagged.
- Reference-set construction: encoded image-post values expanding to every
  constituent file id; the zero-rows guard throwing. This is a separate pure
  function from `planOrphans`, which receives an already-built set.
- `credentials.ts`: expiration decoded correctly from the `exp` claim; provider
  returns refreshed credentials on re-invocation (mocked `getSession`); missing
  session throws.
- `s3Adapter`: against `aws-sdk-client-mock`, asserting bucket, key,
  content type, and progress-percentage math.
- `publicUrl`: default construction and `NEXT_PUBLIC_MEDIA_BASE_URL` override.

## Verification

- Enable the S3 connection toggle in Storage settings.
- Perform a real browser upload of a file large enough to trigger multipart, and
  confirm CORS exposes the `ETag` response header. Multipart cannot complete
  without it.
- Confirm progress reporting still advances smoothly in the post creation UI.
- Compare `next build` output before and after to confirm the feed route bundle
  did not grow.
- Run `orphans` in report mode against a real bucket and sanity-check the count
  before ever passing `--delete`.

## Out of scope

- Upload cancel UI.
- Migrating reads off public URLs.
- Tightening the `media_authenticated_delete` RLS policy. It currently permits
  any authenticated user to delete any object in the bucket. This is a
  pre-existing issue, noted here because it was found during design, and should
  be addressed separately.
